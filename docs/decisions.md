## ADR-0001
**Collector/server language = Java + Spring Boot** · 2026-08-21 · Accepted
- **Context:** Need a language/framework for the collector agent and central server; also aligning with the user's job-search skill targets (Java/Spring is a "have").
- **Decision:** Java 21 + Spring Boot for both agent and server. `[ASSUMPTION: Java 21 until Phase 0 pins exact versions.]`
- **Alternatives:** Go (great gRPC ergonomics, but off the user's skill target) · Node/TS (already covered by the dashboard).
- **Consequences:** Production-shaped, keeps the tool real; slightly heavier than Go for a collector agent. Pin versions in Phase 0.

## ADR-0002
**Scope = full arc (Phases 0–7); ship-after-Phase-4 is the plan of record** · 2026-08-21 · Accepted
- **Context:** ~10 hrs/week bandwidth; full arc re-baselined to ~24–34 weeks (gRPC/RAG/K8s/Terraform all from zero).
- **Decision:** Build toward the full arc but treat **Phase 4** (`v0.1.0-rc`, self-hostable web tool) as the real ship target; Phases 5–7 = v0.2.
- **Alternatives:** Commit to full 0–7 upfront (scope-creep risk) · Stop at Phase 1 CLI (under-delivers on skills).
- **Consequences:** Hard shippable checkpoints at Phases 1, 4, 7 protect momentum; 5–7 explicitly deferrable.

## ADR-0003
**Two Postgres instances: monitored (read-only) + metadata (pgvector)** · 2026-08-21 · Accepted
- **Context:** Must never mutate the user's monitored DB; also need our own store for snapshots/recs/embeddings.
- **Decision:** Monitored DB touched read-only only; PgLens runs a separate metadata Postgres with pgvector.
- **Alternatives:** Store metadata inside the monitored DB (violates safe-by-default; pollutes user's DB).
- **Consequences:** Clean safety boundary; a real growing schema to dogfood indexing on; one more service to run (acceptable, Compose-managed).

## ADR-0004
**Deterministic core, LLM as an optional layer** · 2026-08-21 · Accepted
- **Context:** LLM tools that "explain plans" are commoditizing and can hallucinate; trust is the product.
- **Decision:** The analyzer produces a correct, explainable result with zero LLM. The LLM only phrases facts the core owns. Tool is fully useful with the LLM off.
- **Alternatives:** LLM-first analysis (untrustworthy, non-reproducible).
- **Consequences:** Trustworthy output; graceful degradation; clear boundary the LLM cannot cross (it never invents numbers or DDL).

## ADR-0005
**HypoPG for index validation** · 2026-08-21 · Accepted
- **Context:** Suggesting an index is easy; proving it helps without building it (minutes on big tables) is the hard, valuable part.
- **Decision:** Validate recommendations with HypoPG (hypothetical indexes) → real planner-cost delta. Only surface recs whose cost win clears a threshold.
- **Alternatives:** Actually build indexes to measure (slow, invasive) · pure heuristics (false positives).
- **Consequences:** Honest "expected improvement." **Limitation:** HypoPG covers btree/brin/hash/bloom + partial only; GIN/GiST (LIKE `%…%`, jsonb, full-text) are surfaced but labeled *not planner-validated* — must catch the unsupported-AM error. (See ADR linkage in `docs/architecture.md`.)

## ADR-0006
**Local LLM (Ollama) for privacy** · 2026-08-21 · Accepted
- **Context:** Target user wants query text to stay inside their infra; hosted AI-EXPLAIN tools send it out.
- **Decision:** Use local Ollama; no query text sent to any third-party LLM service.
- **Alternatives:** Hosted LLM API (better quality, breaks the privacy differentiator).
- **Consequences:** Sharpest differentiator vs competitors; quality bounded by local models; degrade gracefully when none configured. **Claim narrowed to:** "no query text is sent to a third-party LLM."

## ADR-0007
**AI-context system: lean CLAUDE.md + progressive-disclosure docs + separate memory** · 2026-08-22 · Accepted
- **Context:** Long, multi-session project at ~10 hrs/wk; need low token usage and correct context recovery every session. Researched 2026 best practices (Anthropic context-engineering guidance + CLAUDE.md guides).
- **Decision:** (a) `CLAUDE.md` < 200 lines = lean pointers only, loaded every turn. (b) Detailed context in `docs/` read on demand (project/architecture/decisions/phases/workflows/glossary). (c) Path-scoped `.claude/rules/*.md` for module-local conventions (loaded only when matching files are touched). (d) Keep repo docs (authored truth) separate from Claude auto-memory (`MEMORY.md` index = accumulated learnings). - **Consequences:** Lower per-turn token cost; fast context recovery; clear ownership of each info type. Requires discipline: update `project.md`/`decisions.md` as work happens (encoded in the CLAUDE.md session protocol).

## ADR-0010
**Phase 0 tooling: defer Java build tooling; CI = lint-artifacts + compose smoke** · 2026-08-24 · Accepted
- **Context:** The user's Phase 0 plan listed Gradle multi-module + Spotless/Checkstyle + Testcontainers "from day 1." But Phase 0 ships **no Java** — its artifacts are Docker, SQL, shell, Makefile, Markdown. Standing up a Java test harness before any Java product code is premature (YAGNI/KISS).

- **Alternatives:** (a) Gradle skeleton now (hygiene-from-day-1, but nothing to build); (b) full Testcontainers now (heaviest; provisions JDK 21 for a test with nothing to test).

Testcontainers pattern gets its first real use in Phase 1.

## ADR-0011
**Postgres image strategy: custom monitored image, pinned versions, pg16** · 2026-08-24 · Accepted
- **Context:** hypopg is not in the stock `postgres` image (the plan's #1 risk); images should be reproducible.
- **Decision:** Build a 2-line `monitored/Dockerfile` `FROM postgres:16-bookworm` that installs `postgresql-16-hypopg` from PGDG (the repo the official image already configures). Pin all images to exact versions (`pgvector/pgvector:0.8.6-pg16`). Stay on **Postgres 16** (conservative; hypopg packaged and confirmed) rather than 17/18.
- **Alternatives:** find a community image bundling hypopg (opaque, unpinned); build hypopg from source (heavier); rolling `:pg16` tag (non-reproducible).
- **Consequences:** Reproducible, transparent, minimal. `pg_stat_statements` is enabled at server start via `shared_preload_libraries` in the compose `command` (an `ALTER SYSTEM` after boot would not load it). **Observed & noted for Phase 1:** `pg_stat_statements.track=all` captures per-row FK-check trigger statements during bulk seed (~500k calls) — revisit `track=top` vs `track=all` when building the ranker so internal RI checks don't pollute the leaderboard.

## ADR-0012
**Phase 1 engine architecture: Spring Boot CLI + reusable engine library with a pure/IO split** · 2026-08-25 · Accepted
- **Context:** Phase 1 ships a `pglens scan` CLI, but the analysis logic must be reusable by the Phase 2 server and collector — it can't be welded to the CLI. User confirmed Spring Boot for the CLI (consistent with ADR-0001).
- **Decision:** Two Gradle (Kotlin-DSL) modules. `:engine` library = **pure-analysis** packages (`model/parse/detect/candidate/rank`, zero Spring imports, Jackson allowed) + a thin `db` **I/O** half (spring-jdbc) wired by a `PgLensEngine` facade. `:cli` = Spring Boot app using **picocli core** + a ~15-line Spring `IFactory` (resolves commands as beans), **not** `picocli-spring-boot-starter` (its latest 4.7.7 is only tested to Boot 3.1.2, vs pinned Boot 3.5). Java 21 via a Gradle toolchain (host runs JDK 17). Spotless (google-java-format) is the style source of truth.
- **Alternatives:** Single module (couples analysis to Spring/CLI, blocks Phase 2 reuse) · picocli-spring-boot-starter (stale vs pinned Boot).
- **Consequences:** The pure half unit-tests with no container and migrates unchanged into the Phase 2 server; the I/O half moves to the collector. Requires discipline to keep Spring out of the pure packages (review now, ArchUnit later). The facade holds one `SingleConnectionDataSource` per scan (HypoPG needs a single session).

## ADR-0013
**Plan capture = EXPLAIN (GENERIC_PLAN); real ANALYZE execution deferred (guard only)** · 2026-08-25 · Accepted
- **Context:** `pg_stat_statements` stores normalized `$1` text with no literals. We need a plan *without executing* on the monitored DB (safe-by-default) and *without inventing* literals (no fabricated evidence).
- **Decision:** Capture `EXPLAIN (GENERIC_PLAN, VERBOSE, FORMAT JSON)` (PG16+). Every cost is labeled a *generic-plan planner estimate*; the real measured "before" is pgss `mean/total_exec_time`, shown beside it. `--explain-analyze` (needs literal synthesis + real execution) is deferred — only its non-SELECT **refusal guard** is in scope. Requires pgjdbc `preferQueryMode=simple` so `$N` reaches the server as literal text (default extended protocol treats it as a bind param and fails).
- **Alternatives:** EXPLAIN ANALYZE with synthesized literals (executes on the monitored DB — unsafe, complex) · plain EXPLAIN of literal-substituted text (fabricates a data distribution).
- **Consequences:** Safe, no execution. Generic default-selectivity can **overstate** skewed-column wins → every number labeled + pgss mean shown; HypoPG is the real cost gate. `PlanCapturer` skips (returns empty) any statement that can't be generic-planned rather than crashing.

## ADR-0014
**Ranker hygiene: toplevel + current-dbid + utility/self filtering (resolves ADR-0011 open item)** · 2026-08-25 · Accepted
- **Context:** ADR-0011 flagged that `track=all` records ~500k nested FK-check trigger statements that would swamp the leaderboard.
- **Decision:** `StatsReader` filters `pg_stat_statements` to `toplevel = true`, the current database (`dbid`), and drops utility statements (regex on the leading keyword) plus PgLens's own introspection (`pg_stat_statements` / `hypopg` text). The ranking column is chosen from a fixed enum (`total|mean|calls`) — **never** interpolated from user input. `--min-calls` floor (default 20). Truncation flagged via `octet_length(query) >= track_activity_query_size`.
- **Alternatives:** Switch the monitored server to `track=top` (loses nested insight globally; not our call to make on someone's DB) · post-filter in Java (ships noise over the wire).
- **Consequences:** Clean leaderboard; nested RI-check noise gone; resolves the ADR-0011 open question. Verified by a deterministic Testcontainers test (call-count / ordering / filter assertions — never wall-clock, so CI-stable).

## ADR-0015
**Anti-pattern detection = pure rules over a plan + catalog snapshot; liberal rules, HypoPG gates; MVP set R1/R3/R4** · 2026-08-25 · Accepted
- **Context:** Under GENERIC_PLAN there are no ANALYZE actuals, so detection needs catalog facts (`reltuples`, existing indexes) as *input*. The phase plan proposed rules R1–R6.
- **Decision:** `CatalogReader` (I/O) builds a pure `CatalogSnapshot` (row-count estimates + indexes); the `detect` package is **pure** (Strategy `Rule`s consuming plan + catalog), so rules are fixture-testable offline. Rules are deliberately **liberal** — they flag the pattern; **HypoPG validation downstream is the decisive gate** (this is what makes over-recommendation safe). MVP ships **R1** (selective seq-scan filter on an unindexed column), **R3** (unindexed equi-join key — the PK/indexed side is not flagged), **R4** (Sort feeding a Limit, unless an index already leads with the sort column). **R2 (composite) is folded into candidate generation** — a composite index is a *candidate* that emerges by merging an R1 filter finding with an R4 sort finding on the same table (cleaner SOLID split than a rule that overlaps R1+R4 and double-counts). **R5** (row mis-estimation) stays ANALYZE-gated/inactive; **R6** (advisory over-fetch, never an index rec) deferred as lowest-value.
- **Alternatives:** Strict rules that pre-judge cost (duplicate HypoPG, risk false negatives) · a standalone R2 composite rule (overlaps R1+R4).
- **Consequences:** Detection is pure and offline-testable — verified against 5 real captured plans (per-rule + negatives) and confirmed to fire correctly on the **live** planner's current plan shapes. Column extraction is regex over EXPLAIN VERBOSE's qualified expressions: MVP handles `col <op> $N` and `a.x = b.y`; a param on the far side of an expression, and merge/nested-loop join conditions, are later refinements. Tables are keyed by unqualified name (single-schema assumption). **Renumber note:** the validation-gate & GIN/GiST-labeling ADR (provisionally 0015 in the phase plan) is recorded as **ADR-0016**.

## ADR-0016
**HypoPG validation gate = index used + relative cost drop ≥ threshold; GIN/GiST & missing-hypopg → labeled not-validated** · 2026-08-25 · Accepted
- **Context:** Rules generate candidates liberally (ADR-0015). Something must decide, honestly, which candidates are real wins — without building indexes and without fabricating numbers (charter principle #1) — and label everything as what it is (charter principle #6).
- **Decision:** `HypoPGValidator` (I/O) creates a **hypothetical** index (`hypopg_create_index`), re-EXPLAINs the query under GENERIC_PLAN, and keeps the candidate only if the hypothetical index is **actually used** in the re-planned tree **AND** total cost drops by ≥ a threshold (**provisional 15%**, configurable). Used-gate is primary; otherwise `SUPPRESSED` (distinguishing "planner ignored it" from "win too small"). Every candidate returns a `Recommendation` (validated / suppressed / not-validated) — nothing is silently dropped, so the report can be honest about what was tried. **Graceful degradation:** GIN/GiST (HypoPG can't simulate), a missing `hypopg` extension, or an unexplainable query → `NOT_PLANNER_VALIDATED` with a labeled reason, never a crash. Every cost is labeled a generic-plan **planner estimate**, not a runtime measurement.
- **Safety invariants:** runs on the single scan connection (HypoPG is session-local); `hypopg_reset()` after **every** candidate so candidates are validated in isolation and none leak; verified `SELECT count(*) FROM hypopg() = 0` after each run. Nothing is ever built on the real database.
- **Alternatives:** Build real indexes to measure (slow, invasive, mutates the monitored DB — violates safe-by-default) · trust the rules without validation (false positives — the thing this project exists to avoid) · fixed absolute cost-delta threshold (not comparable across queries; relative % is).
- **Consequences:** False-positive recommendations are killed at the planner, not guessed. Verified end-to-end on a seeded+ANALYZEd DB: high-cardinality `customer_id` → **validated** (used, real cost drop); single-value `status` (n_distinct=1) → **suppressed** (planner ignores it); a strict threshold suppresses a genuine-but-small win; GIN → not-validated. **Known honesty gap (documented, per the plan's risk section):** generic default-selectivity can *overstate* skewed-column wins → high-value recs warrant literal corroboration (a later phase); the 15% threshold is provisional and revisited with real spike numbers.

## ADR-0017
**Cross-query recommendation ranking = real total time × validated relative drop; near-duplicate dedupe by btree-prefix coverage (flag, never sum)** · 2026-08-25 · Accepted
- **Context:** A scan analyzes several queries; each yields validated index recommendations (ADR-0016). Two decisions remain: how to *order* them into one "top recommendations" list, and how to avoid advising two overlapping indexes (the plan's over-recommendation risk).
- **Decision:** The pure `Recommender` (package `rank`) ranks only **planner-validated** recs by **score = the query's real `pg_stat_statements` total_exec_time × the HypoPG generic-plan relative cost drop** — a real measured weight scaled by an estimated fraction. This deliberately ranks a *modest* estimated win on a hot query **above** a *large* estimated win on a cold one (proven by test). Suppressed / not-validated recs are surfaced per-query by the renderer, not ranked here. **Dedupe:** since a btree on `(a, b)` already serves lookups on `(a)`, a recommendation whose key columns are a **prefix of (or equal to)** another's on the *same table and access method* is redundant; the more general index is kept and the covered one is **flagged `subsumedBy` it, not dropped** (so the report stays honest about what was covered). Processing most-general-first (longest key, higher score breaking ties) guarantees the general index is kept before the prefixes it covers, and exact duplicates keep the higher-scoring instance.
- **Alternatives:** Rank by relative drop alone (a huge % on a query that runs twice a day outranks a real workload win — dishonest weighting) · rank by raw total time alone (ignores whether the index actually helps) · **sum** a subsumed rec's benefit onto the survivor (fabricates an aggregate HypoPG never validated — each candidate was validated only against its own query's plan; violates charter principle #1) · silently drop covered recs (hides what was considered).
- **Consequences:** The score is an **estimate label everywhere** (`estimatedMsSaved`), never presented as measured savings; the real measured signal shown beside it is the query's pgss mean/total time. Dedupe is btree-coverage-aware only (different columns or different access method never subsume). The survivor keeps its own validated score — the ranking can therefore under-weight a general index that also serves a hotter query's prefix rec, but the prefix rec remains in the output (flagged), so nothing is hidden. Ordering is fully deterministic (score desc, then suggested index name).

## ADR-0018
**`--json` contract = the pure model records serialized as-is (ScanReport v1.0); the scan is query-centric with a cross-query top-recs summary** · 2026-08-25 · Accepted
- **Context:** `pglens scan` needs a stable machine-readable output — the contract Phase 2's collector/server and Phase 4's dashboard consume. It also needs a readable human report. And the engine facade had to grow from stats-only into the full pipeline (capture → detect → propose → validate → rank).
- **Decision:** The `--json` shape **is** the pure `model` record graph — `ScanReport` → `TargetInfo` + `QueryReport[]` (each with `PlanSummary`, `Finding[]`, `Recommendation[]`) + `topRecommendations` (`RankedRecommendation[]`) + `notes[]` — serialized verbatim by Jackson with `NON_NULL` inclusion, so **the contract can't drift from the code** and there is no hand-maintained schema/DTO layer to keep in sync. Versioned by a `schemaVersion` field (**"1.0"**; bump on any breaking change). The report is **query-centric** (a validated rec appears under its query with the full validated/suppressed/not-validated story) **and** carries a **cross-query `topRecommendations`** summary (the ranked, deduped actionable list) — the two views serve different readers without either hiding information. `PgLensEngine.scan()` orchestrates the whole pipeline over the one scan connection; `explain(queryid)` reuses the same per-query `analyze()` step for a single statement. Enum values (status, access method, confidence) serialize as their constant names.
- **Alternatives:** A separate hand-written JSON DTO / schema (drifts from the model, extra surface) · a flat recommendations-only list (loses the per-query evidence, or the cross-query ranking) · annotating model records for presentation (couples pure model to a serialization concern — kept the config in the CLI renderer instead).
- **Consequences:** Verified live against the demo DB: valid JSON, `schemaVersion` 1.0, null costs omitted (not `null`), honesty labels present; human report shows offending node + rule + copy-pasteable DDL + labeled cost delta + real pgss mean-time, and the merged/near-duplicate note. CLI exit codes: **2** usage error, **1** connection/runtime failure (incl. unknown queryid), **0** success. A found-and-fixed bug (R4 evidence had unformatted `%s`/`%.2f` from a `.formatted()` precedence slip) now has a regression assertion. **Deferred to step 12:** a Testcontainers end-to-end test that drives `scan()`/`explain()` and asserts the #8/#10 negatives, GIN labeling, `hypopg()=0`, and read-only enforcement (today proven by the live run).

## ADR-0019
**R7 GIN rule: containment/existence operators become GIN candidates, surfaced but never planner-validated; LIKE-trigram deferred** · 2026-08-26 · Accepted
- **Context:** The phase DoD requires a **GIN fixture** surfaced as *suggested — not planner-validated* (charter principle #6: HypoPG can't simulate GIN/GiST, so never pretend it did). The demo pack had no jsonb fixture, and no rule yet emitted a GIN candidate — the whole not-planner-validated path was proven only from a hand-built candidate, never from a real query.
- **Decision:** Add a pure `GinCandidateRule` (**R7**) that flags a `Seq Scan` whose `Filter` uses a GIN-servable **containment/existence operator** — jsonb `@>`, key-exists `?`/`?|`/`?&`, jsonpath/full-text `@?`/`@@` — on a column no index leads with (a GIN index on the column silences it, same as any other rule). The column+operator are pulled from EXPLAIN VERBOSE's qualified filter text by a new `PlanColumns.jsonbPredicates` regex (longest-operator-first alternation so `?|`/`?&` aren't truncated to `?`). `IndexCandidateGenerator` turns an R7 finding into a **GIN** candidate on that column — a *separate access method*, so it never merges into a btree composite — and `IndexCandidate.of` already routes GIN to the not-planner-validatable bucket, so `HypoPGValidator` returns `NOT_PLANNER_VALIDATED` with a labeled reason and **no cost number**. Demo pack gains **#11** `SELECT count(*) FROM events WHERE payload @> '{"ua":"agent-7"}'` (the seeded `events.payload` jsonb); its test fixture is the **real captured** generic plan, not a hand-written one. **Scope:** only `Seq Scan` filters; the operator set is the GIN-servable ones above; `<@` (contained-by) is excluded (ambiguous between jsonb and range/GiST when the column type is unknown). **LIKE `'%…%'` trigram GIN is deliberately deferred** — it needs the non-default `pg_trgm` extension + a `gin_trgm_ops` opclass and has no demo fixture; adding it now would be untested speculative generality (YAGNI).
- **Alternatives:** Reuse R1 for jsonb (R1's `predicateColumns` only matches scalar `<op> $N`, and the candidate would be a wrong btree) · emit the GIN candidate but *guess* a cost by running an approximate btree (fabricates a number HypoPG never validated — violates #1/#6) · include `<@` and full LIKE detection now (over-reach without fixtures to keep them honest) · put the DDL opclass (`jsonb_path_ops`/`gin_trgm_ops`) in the candidate (we can't know the column type from the catalog snapshot — keep the default `USING gin (col)` and let the not-validated label carry the caveat).
- **Consequences:** The not-planner-validated path is now exercised by a **real query end-to-end**, not just a synthetic candidate. Verified live: #11 detected by R7, rendered `[not planner-validated] CREATE INDEX … USING gin (payload)` with no delta, **excluded** from the planner-validated top-recs list, and the standing safety invariants held (`hypopg() = 0`, zero real indexes created). Because the catalog carries no column types, R7 can in principle flag an array/range `@>`; the GIN suggestion is still reasonable and, being unvalidated and labeled, is low-risk. Detection stays pure and offline-testable (regex + rule + generator unit tests over the captured fixture). **Deferred (step 12):** the Testcontainers end-to-end test will assert GIN labeling on #11 alongside the #8/#10 negatives.

## ADR-0020
**Safety: enforce read-only at the database via session characteristics on the single scan connection; prove the whole pipeline (and read-only) with an E2E Testcontainers test; add a Java CI job** · 2026-08-26 · Accepted
- **Context:** Charter principle #2 (safe-by-default) and the phase DoD require that PgLens can never write to the monitored DB and that a write is *rejected*, not merely avoided. The plan's safety model called for read-only enforced at the DB via explicit SQL. The as-built engine, however, only set `statement_timeout`/`lock_timeout` on the scan connection — read-only was **not** actually enforced (a latent gap: nothing in the pipeline writes, but nothing stopped a write either). Phase 1 also needed its end-to-end proof (`scan()`/`explain()` across a full multi-query scan) and a CI job to run the Java build.
- **Decision:** Move session setup into `DataSources.applySessionGuards(JdbcTemplate)` and make its **first** statement `SET SESSION CHARACTERISTICS AS TRANSACTION READ ONLY` (then the two timeouts). Under the reused single connection with autocommit, every subsequent statement runs in an implicitly read-only transaction, so Postgres itself rejects `INSERT`/`UPDATE`/`DELETE`/DDL — and any `EXPLAIN ANALYZE` of a write — with "cannot execute … in a read-only transaction", **driver-independently**. `PgLensEngine` calls this shared method in its constructor (wrapping failure as a connection error) and exposes a small `hypotheticalIndexCount()` safety probe (`SELECT count(*) FROM hypopg()`) so the leftover-index invariant is assertable on the real scan connection. Verified empirically first that HypoPG's create-index / re-EXPLAIN / `hypopg_reset()` all work under a read-only session (HypoPG is designed for read-only/standby use) — so enforcement costs nothing. New `PgLensEngineIntegrationTest` (Testcontainers, real monitored image) seeds a small ANALYZEd dataset, **resets `pg_stat_statements`** for a deterministic leaderboard, warms three representative statements, then drives one `scan()` and asserts: the selective filter is planner-validated and reaches the cross-query top list; the jsonb `@>` query yields a GIN rec that is `NOT_PLANNER_VALIDATED` with null costs and is kept out of the validated top list; the `GROUP BY status` aggregate yields no validated rec; `hypotheticalIndexCount() == 0` after the scan; `explain(id)` round-trips and an unknown id is empty; and `applySessionGuards` makes writes fail with a read-only error. CI gains a `build` job: setup JDK 21 → `docker build` the monitored image → `./gradlew build` (Spotless + unit + integration), beside the existing lint + compose-smoke jobs.
- **On the deferred ANALYZE statement-tag guard:** the plan described a pre-parse guard that refuses non-SELECT for `--explain-analyze`. That flag isn't wired (real ANALYZE execution is deferred, YAGNI), and building a parser for a non-existent path would be dead speculative code. Read-only enforcement is the stronger, load-bearing guarantee — it makes *any* write impossible regardless of statement tag — so the DoD's "non-SELECT ANALYZE refused" is satisfied by the real mechanism (proven: an `UPDATE` is rejected). The statement-tag guard ships with the analyze feature in a later phase.
- **Alternatives:** Per-unit `TransactionTemplate` with `SET TRANSACTION READ ONLY` (the plan's original shape — heavier; the whole scan is one connection so a session-level default is simpler and equivalent) · rely on pgjdbc's `readOnly=true` (driver-specific; the plan noted a framework flag alone doesn't block writes) · a DB-level read-only **role** (correct end state, but deferred to Phase 2 when the agent connects) · assert read-only only in a unit test (can't prove it without a real server).
- **Consequences:** The monitored DB is now safe by construction — writes are rejected at the source, and the E2E test proves it on the real image. The `hypopg() = 0` invariant is asserted across a full multi-query scan (not just per-candidate). Phase 1 is code-complete and CI-covered; the only remaining item is tagging `v0.0.1` (on user go-ahead). A `hypotheticalIndexCount()` method is now public API on the facade — a legitimate safety probe, kept minimal.

## ADR-0021
**Verification hardening: typed-literal capture, R1 range predicates, self-introspection hygiene, and centralized rule thresholds** · 2026-08-26 · Accepted
- **Context:** An unbiased end-to-end re-verification of Phase 1 found the DoD item *"every `demo/slow_queries.sql` anti-pattern is detected"* was **not truthfully met**: demo **#3** (`orders WHERE created_at >= now() - interval '7 days'`) produced no finding. Root cause was two stacked defects — (a) `pg_stat_statements` normalizes the typed literal `interval '7 days'` to `interval $1`, which is a **syntax error to EXPLAIN** (`syntax error at or near "$1"`), so plan capture failed silently and the query was skipped (`planCaptured=false`); this drops *any* real query using `interval/timestamp/date/… '…'` literals, not just the demo — and (b) even with a plan, R1's predicate regex only matched `col <op> $N`, never `col <op> <expr containing $N>`. A third finding: PgLens's own catalog-introspection queries (`CatalogReader`'s `pg_class`/`pg_index`, the `pg_extension` probes) were **not** excluded from the leaderboard, contradicting ADR-0014's stated "drop pglens-own statements" intent (visible at low `--min-calls`, and accumulating a call every scan). (The 225 IDE "red squiggles" were separately diagnosed as a stale VS Code Gradle sync — Gradle compiles clean — not a code defect.)
- **Decision:** (F1) `PlanCapturer.normalizeTypedLiterals` rewrites a `TYPE $N` remnant to the equivalent cast `$N::TYPE` before EXPLAIN (bounded, ordered alternation of the SQL types that use `TYPE 'literal'` syntax; multi-word types precede their prefixes). Empty-on-failure fallback is unchanged, so a bad rewrite is no worse than before. (F2) `PlanColumns.predicateColumns` now matches `qualifier.column <op>` and inspects the right operand: accept when it contains a bound `$N` and does **not** begin with another qualified column (a join → still R3's job), so `col = $1` and `col >= now() - $1` both qualify while `a.x = b.y` does not. (F3) PgLens's own introspection queries carry a `/*pglens:introspection*/` marker (`DataSources.INTROSPECTION_MARKER`; pg_stat_statements retains the comment) and the ranker's hygiene adds `NOT LIKE '%pglens:introspection%'`. Housekeeping: rule magic-numbers move into a package-private `DetectionThresholds` (`MIN_TABLE_ROWS` — previously duplicated in two rules — `LARGE_TABLE`, the selectivity bands); `StatsReader`'s duplicated pg_read_all_stats error is one helper; `DataSources` session/connection literals are named constants; the most verbose javadocs were trimmed to point at the ADRs.
- **Alternatives:** Skip `#3` as "an unfixable pgss quirk" (false — the cast rewrite is safe and general; leaving it silently drops real slow queries) · a dedicated range-only rule instead of broadening R1 (more code for the same detection; R1 already owns indexable filters) · exclude introspection by catalog-name matching (brittle — a marker comment is exact and survives normalization) · assert #3 as a *suppressed* rec (the real HypoPG verdict on the demo is **PLANNER_VALIDATED −50.7%**, so honesty means reporting the validated win) · a global constants file (over-centralizes rule-local values; `DetectionThresholds` stays inside `detect` for locality).
- **Consequences:** #3 is now captured, R1-detected, and **HypoPG-validated as `btree(orders.created_at)` −50.7%** (a real generic-plan estimate, verified live), so it joins the actionable top recs — the DoD item is met truthfully, not by rewording. The typed-literal fix generalizes to any real DB. PgLens no longer ranks its own queries (verified live: 0 self-rows in the leaderboard). **+8 tests → 82 green** (a pure `normalizeTypedLiterals` unit test, a real captured `orders_created_at_range.json` fixture + R1 range test, the join-vs-filter boundary, a marked-introspection hygiene assertion, and an E2E test that the typed-literal query is captured + detected + HypoPG-processed). Safety invariants unchanged (`hypopg()=0`, zero real indexes).

## ADR-0022
**Capture-robustness harness + deferred-work backlog + index-hygiene pre-committed to Phase 2** · 2026-08-27 · Accepted
- **Context:** Between Phase 1 and Phase 2, the user raised four ideas: (1) split reads/writes so reads use real `EXPLAIN ANALYZE`; (2) find another library for GIN/GiST; (3) grow the anti-pattern rule set; (4) grow the query dataset to find bugs. Independent review (grounded in the code + verified against HypoPG's docs and C source) concluded: (1) is a premise error — GENERIC_PLAN is a *no-literals + no-execution-on-prod* choice, not a write-avoidance one, so the read/write split unlocks nothing; the honest "real numbers" path is opt-in execution on a **non-prod** target (defer). (2) is a dead end — HypoPG (`hypopg_index.c`) supports **btree/brin/hash/bloom only** and rejects the rest (`access method "%s" is not supported`); GIN/GiST are *fundamentally* unsimulatable (their cost model needs a built index's internal stats), so the current *not-planner-validated* labeling is already state-of-the-art (defer). (3) is worthwhile but engine polish, and the highest-ROI piece (index hygiene) *wants* Phase 2's history. (4) is the strongest and cheapest — PgLens's worst bug to date (ADR-0021) was exactly a real query shape the neat demo never exercised, and plan **capture** is the fragile surface (a normalized statement that can't be `EXPLAIN (GENERIC_PLAN)`'d is dropped with no finding).

(b) **Start `docs/backlog.md`** — a durable, contributor-facing record of consciously-deferred work (What / Why deferred / Constraints / Effort / Refs; `good-first-issue` vs `needs-design` tags), seeded with ideas 1/2/3's deferred pieces (B1–B9). (c) **Pre-commit index hygiene (unused + duplicate indexes) to Phase 2** (backlog B5, but *owned by* Phase 2) — recorded in `docs/project.md` → Phase 2 pre-commitments so plan-verification folds it in.
- **On the one real finding:** the harness immediately caught `col = ANY (ARRAY[$1, $2, …])` on a **non-text** column failing capture — normalization types the `$N` as `text`, so GENERIC_PLAN sees `integer = ANY(text[])` → "operator does not exist". A safe fix needs catalog-type-aware rewriting (backlog **B9**); the commoner forms (`col IN ($1,…)`, `col = ANY ($1)`) capture fine, and the skip is **surfaced** (query still ranks `planCaptured=false`; renderer prints "plan not captured … skipped"), so it's a labeled limitation, not the ADR-0021 *silent* class. - **Consequences:** The silent-skip regression class is now guarded in CI by a measurable skip-rate, and the fragile regex/capture surface has explicit capability+boundary tests. `docs/backlog.md` gives future sessions (and OSS contributors) a reasoned menu instead of re-litigating settled deferrals — and keeps the "no fabricated evidence / safe-by-default" invariants attached to each deferred item. **90 tests green (68 unit + 22 IT)**; full `./gradlew build` green. Engine code paths unchanged (test-only + docs); all safety invariants intact. No new engine features shipped — this is hardening + planning, consistent with "ship each phase" (Phase 2 is where the next feature lands).

## ADR-0023
**Phase 2 topology = `a-pull`: edge HypoPG validation via agent-lease; no bidirectional stream** · 2026-08-29 · Accepted
- **Context:** Phase 2 splits the CLI into a collector `agent` next to each monitored DB and a central `server`. HypoPG is session-local on the monitored DB, so index validation needs a connection *to that DB*; the privacy posture wants that connection to stay at the edge. But the agent is a dial-*out* client (private network, usually un-dialable), so a plain server→agent unary `ValidateIndex` call is impossible. The user's Phase 2 plan framed this as a binary: **(a)** one *bidirectional* stream the agent opens (server pushes validate-requests down it) vs **(b)** server-side validation against a read replica (server holds a DB connection). Researched both against real-world collectors and gRPC operational facts.
- **Decision:** Neither. Choose **`a-pull`** — edge validation, but the agent **leases** validation work instead of the server pushing it down a live stream. Contract: `Ingest.StreamSnapshot` (client-streaming, short-lived per interval) carries samples/catalog/text up; `Validation.LeaseValidations` (server-streaming) hands the agent pending candidate DDLs on the agent's own cycle; `Validation.ReportValidations` (client-streaming) returns HypoPG cost deltas; `Health.Check` (unary). The agent stays a pure dial-out client the server never dials into. This maps directly onto the engine's existing pure/IO seam (ADR-0012): the `db` half (`StatsReader`/`CatalogReader`/`PlanCapturer`/`HypoPGValidator`) runs in the agent, the pure half (`parse`/`detect`/`candidate`/`rank`) runs in the server — **no engine rewrite**.
- **Alternatives:** **(a) live bidi** — the plan's recommendation. Rejected: a long-lived bidi stream is idle-timeout-killed by load balancers (AWS ELB ~60s, GCP ~10min) so it needs keepalive babysitting; it **pins to one server instance** (loses per-message load-balancing) — the exact mechanism behind the plan's own §4c horizontal-scaling worry; and it head-of-line-blocks sample flow behind validation round-trips. It teaches the bidi mechanic but fights the scaling goal. · **(b) server-side replica** — simplest RPC, but the server needs a read-only connection + credentials to *every* monitored DB (erodes the "DB access stays at the edge" story) and requires actually running a replica; least gRPC learned. · **fat agent** (run the whole pipeline at the edge, stream finished recs) — max privacy but abandons the central-analysis design and re-runs analysis on every host; the privacy gain is marginal since normalized text/plan already reach the server for analysis.
- **Consequences:** All calls are short-lived, retryable, and load-balanceable → satisfies the §4c HPA goal instead of fighting it (paired with the ADR-0028 advisory-lock singleton for the analysis job). Exercises **three** gRPC modes (unary + client-streaming + server-streaming) + interceptors; **bidirectional streaming is consciously not built** — recorded as a deliberate trade, not an omission, and a stronger senior signal ("evaluated bidi, chose the pattern that scales") than checking the bidi box. Real-world corroboration: the closest analog (pganalyze collector) is agent-push and the server never dials back. If a future phase needs sub-second validation latency, a live push path can be added without breaking the lease contract.

## ADR-0024
**Server-side, ack-anchored delta computation; reset via global `pg_stat_statements_info.stats_reset` (PG16) + a per-query regression guard** · 2026-08-29 · Accepted (corrected same-day — see Correction)
- **Context:** `pg_stat_statements` counters are cumulative; trends need per-interval **deltas**. The user's plan put delta computation in the agent ("compute deltas against the previous snapshot"). Deltas must survive `pg_stat_statements_reset()`, entry **eviction** (pgss has a bounded hash; least-used entries are evicted and may reappear), and a mid-stream server outage — without gaps or double-counting (plan §10 self-check).
- **Decision:** The agent forwards **raw cumulative** counters + its sample time + the monitored server's global **`pg_stat_statements_info.stats_reset`** (one timestamp per batch); the **server** computes deltas against the **last persisted** snapshot for `(db_id, queryid)`. Reset detection: the server stores the last `stats_reset` it saw per db (`monitored_dbs.last_stats_reset`); if an incoming batch reports a **later** value, a global `pg_stat_statements_reset()` happened, so every query's interval delta is its **current** cumulative (post-reset activity) rather than `current − stale-baseline`. This is precise even for a very hot query that ran more than its whole prior history in one interval — a case a "counters went down" heuristic misses. A **per-query regression guard** (current < previous with no global reset) additionally catches a per-entry eviction/targeted reset the global signal can't see. `mean_exec_time` is **derived** (`total_delta / calls_delta`), never the sampled lifetime mean (a fabricated interval number — charter principle #1). The cross-send **no-double-count guarantee is the atomic anchor-advance** — a lost send doesn't advance the anchor, a committed one does, both in a single batch transaction — **not** the `INSERT … ON CONFLICT (db_id, queryid, captured_at) DO NOTHING` (that guards only a *within-batch* duplicate `queryid`; `captured_at` is server-assigned, so a hypothetical replay would get a fresh timestamp and not collide anyway). `captured_at` is deliberately the server receive time (the skew-immune trend axis + PK), not the agent's sample epoch — keying idempotency on the agent's clock would reintroduce skew into the axis. [G7 correction, ADR-0035.]
- **Alternatives:** Agent-side deltas (the plan) — makes the agent stateful (must remember baselines across restarts), pushes reset logic to every edge, and needs disk-buffering to not lose a window on server downtime. · A pure "counter went backwards" heuristic — misses the reset-then-heavy-load case for hot queries (counters don't drop below the stale baseline); the global `stats_reset` signal is exact for full resets. · Per-entry `stats_since` — the cleanest signal, but it **only exists in pgss 1.11 (PG17)**; we pin **PG16** (ADR-0011), whose pgss tops out at 1.10 (verified from the image's extension SQL files). · Store only deltas (no cumulative) — then the next delta has no baseline after a lost send.
- **Consequences:** The agent is **stateless and thin** (sample → send → forget); the delta/reset logic is plain-**unit-testable with no DB** and the reset path is proven end-to-end (an IT streams two batches with an advanced `stats_reset` and asserts the post-reset delta is the current cumulative, not a negative). Anchoring to the last *persisted* snapshot makes the plan's §10 self-check hold **for free**: a lost/failed send means the next accepted snapshot's delta spans the gap → no data gap, no double-count, **no disk buffer needed** (disk-spool consciously dropped as YAGNI). The same machinery serves index-hygiene (`pg_stat_user_indexes.idx_scan` deltas over the window; ADR-0029).
- **Known limitation (the one case the two PG16 signals miss):** the global `stats_reset` + regression guard is the *complete* pre-PG17 signal set, but there is a single residual blind spot — an entry **evicted and recreated between two samples** (no global reset) that, post-recreation, accrues *beyond* its prior cumulative in that one interval. Then `current > previous` (regression guard doesn't fire) and no global reset was reported (`stats_reset` unchanged), so that interval's delta is over-counted for that **one** query. It self-corrects the next interval and never produces a negative. PG17's per-entry `stats_since` is the only signal that closes it (the creation timestamp moves forward); on PG16 it is an accepted, labeled edge — not a fabricated number, just a rare one-interval over-estimate. Verified against the real image on 2026-08-29 (`pg_stat_statements_reset(userid,dbid,queryid)` does **not** bump the global `stats_reset` per the PG17 docs, which is precisely why the regression guard is required alongside it, not redundant).
- **Correction (2026-08-29):** The original decision named per-entry `pg_stat_statements.stats_since` as the reset signal and claimed it shipped in pgss 1.10/PG16. That was a factual error surfaced during implementation: extending the engine's `StatsReader` to read `stats_since` failed against the real monitored image with "column does not exist". `stats_since`/`minmax_stats_since` were added in **pgss 1.11 (PostgreSQL 17)**; our PG16 image ships pgss **1.10** (confirmed: the image's `pg_stat_statements--*.sql` files stop at `1.9--1.10`). Rather than bump the whole stack to PG17 (touching ADR-0011's deliberate PG16 pin and the frozen Phase 1 image), the design switched to the **global `pg_stat_statements_info.stats_reset`** (present since pgss 1.9) plus the per-query regression guard — PG16-correct, and it still satisfies the DoD's "correct after a reset (tested)". The engine's `StatementStat` was reverted to its Phase 1 shape (no `stats_since`). Learning captured in memory ([[pgss-stats-since-is-pg17]]).

## ADR-0025

Natural composite PKs where they match the access pattern; `query_stats` PK `(db_id, queryid, captured_at)` gives idempotent ingest. The queue gets two **operational** indexes: a partial index on `state='PENDING'` for tight lease scans and a partial UNIQUE on `(db_id, queryid, candidate_ddl) WHERE state IN ('PENDING','LEASED')` to block enqueuing an in-flight duplicate. **The cross-query time-range ("top movers") trend index is deliberately NOT created in V1** — that gap is the honest dogfood target: backfill weeks of `query_stats`, measure the slow trend query with PgLens itself, add the right index (BRIN on the append-only `captured_at`, or a composite), and record the real before/after in `docs/benchmarks.md`.
- **Alternatives:** Liquibase (heavier XML/changelog model; Flyway's plain-SQL migrations are simpler and SQL is the thing we're teaching) · one wide "snapshots" table (loses the clean cumulative-anchor vs. delta-series split ADR-0024 needs) · pre-adding the time-series index in V1 (would rob the dogfood benchmark of a real before/after — the whole point of §4e) · surrogate keys everywhere (the composite natural keys ARE the query/idempotency shape; a surrogate would need a redundant unique index anyway).
- **Consequences:** Migrations run on boot; proven by a Testcontainers integration test that boots the Spring context against the real pgvector image and asserts the full V1 schema, exactly-one applied migration (idempotent), and the partial indexes exist. The schema evolves additively — index-hygiene columns/tables and the dogfood index land as later migrations (V2…), which also exercises the migration workflow (a Phase 2 learning goal). The validation queue's `FOR UPDATE SKIP LOCKED` lease pattern (Step 5) rides the partial PENDING index.

## ADR-0027
**Agent↔server authentication = per-agent bearer token (SHA-256 hashed at rest) via a gRPC `ServerInterceptor`; mTLS/OIDC deferred** · 2026-08-29 · Accepted
- **Context:** The DoD requires that unknown/unauthenticated agents are rejected — PgLens must never accept anonymous stat uploads. The plan offered a per-agent token (bootstrap) and/or mTLS. Dashboard OIDC is already Phase 6.
- **Decision:** Each agent presents a per-agent bearer token in gRPC metadata (`x-pglens-token`). A single `AuthInterceptor` (grpc-java `ServerInterceptor`) SHA-256-hashes the presented token, resolves it to a `monitored_dbs` row by `agent_token_hash`, pins the resolved `MonitoredDb` into the gRPC `Context`, and closes the call with `UNAUTHENTICATED` before the service method runs when the token is missing or unknown. Only the hash is stored (never the raw token). The interceptor wraps the Ingest (and, from Step 5, Validation) services via `ServerInterceptors.intercept`; Health is intentionally unauthenticated. mTLS is **deferred to Phase 6** (hardening) — it adds cert lifecycle/rotation for a marginal gain over a hashed bearer token at Phase 2's threat model.
- **Alternatives:** mTLS now (heavier cert management; the token already meets the DoD and gates every RPC) · a single shared secret for all agents (can't identify or revoke one agent; the per-agent token doubles as the db identity) · authenticate in each service method (duplicated, easy to forget — an interceptor is the single choke point) · store the raw token (needless secret at rest; the hash suffices for lookup+compare).
- **Consequences:** Every ingest/validation RPC is authenticated at one choke point, and the authenticated db flows to the service via the gRPC `Context` (so a batch can't spoof a `db_name` it isn't authorized for). Proven by an integration test over the real transport: a valid token ingests and persists deltas; an unknown token is rejected with `UNAUTHENTICATED`. Token issuance/registration is a bootstrap concern (`MonitoredDbRepository.register`, seeded for the demo in Step 9); a full admin/rotation flow rides Phase 6.

## ADR-0028
**Scheduled analysis is a singleton across replicas via a *transaction-scoped* advisory lock; the catalog is persisted server-side to feed the pure detector** · 2026-08-29 · Accepted
- **Context:** Phase 2 moves the Phase 1 analysis pipeline server-side and onto a schedule: for each monitored db, reuse the engine's pure half (`PlanParser` → `AntiPatternDetector` → `IndexCandidateGenerator`) over the persisted plans + catalog, and enqueue the surviving candidates as validation jobs the agent edge will HypoPG-validate (ADR-0023). Two problems: (a) running N server replicas must not run the analysis N times (double-enqueue, wasted work); (b) `AntiPatternDetector.detect(plan, catalog)` needs a `CatalogSnapshot` (per-table `reltuples` + existing indexes with their leading columns) that only the agent can read from the monitored DB.
- **Decision:** (1) **Singleton via `pg_try_advisory_xact_lock`.** The whole pass runs in one transaction that first tries a transaction-scoped advisory lock on a fixed key; a replica that can't take it skips the tick. Transaction-scoped (not session-scoped) is deliberate — under a pooled `DataSource`, a session lock could be acquired and released on *different* pooled connections; the xact lock is pinned to the transaction's connection and auto-releases at commit. No new dependency (vs. ShedLock), honest about being a down-payment (full stateless/stateful HPA split is Phase 5). (2) **Server-persisted catalog.** The agent sends a `CatalogSnapshot` on the wire (moved here from Step 4, where nothing consumed it); the server **replaces** this db's `table_catalog` + `index_catalog` rows each ingest (small, slow-changing — replace beats upsert-with-stale-rows so a dropped index can't linger and suppress a real recommendation) and rebuilds the engine `CatalogSnapshot` from them for detection. The `.proto` `IndexStat` gained `columns`/`method`/`predicate` (the detection inputs) alongside its existing hygiene fields. (3) **Idempotent enqueue** via the V1 partial-unique `validation_jobs_inflight_uniq` as the `ON CONFLICT` arbiter — re-analysis never double-enqueues a candidate already in flight.
- **Alternatives:** ShedLock / Quartz cluster (a dependency + tables for what one advisory lock does) · session-scoped `pg_advisory_lock` (breaks under connection pooling — see above) · leader election via a `leader` row + heartbeat (more moving parts than a DB-native lock) · recompute the catalog on the server from raw stats (the server has no connection to the monitored DB — that's the whole point of `a-pull`) · keep the catalog only in memory (lost on restart; can't analyze a db whose agent is momentarily down) · upsert catalog rows keeping stale ones (a dropped index would keep suppressing a valid rec).
- **Consequences:** N replicas are safe to run — exactly one analyzes per tick, the rest no-op. The pure engine half is reused verbatim server-side (ADR-0012's split pays off again — zero engine edits for the pipeline itself). Detection runs on a `CatalogSnapshot` rebuilt from persisted rows, proven by an IT (seed a captured seq-scan plan + a large unindexed table → one `BTREE` candidate enqueued PENDING; re-run enqueues no duplicate; an existing index on the filtered column yields no candidate). The queue fills but nothing leases yet — leasing + edge HypoPG + rank is **Step 5b**. The V2 migration adds `table_catalog` and the `index_catalog` detection columns. The hygiene-only `IndexStat` fields (definition/constraint_backed/idx_scan) ride to Step 6 (the step that reads them).

## ADR-0029
**Index hygiene (B5) graduates into Phase 2 as a pure analyzer over a persisted `idx_scan` window; the whole guard (unique/PK/FK/constraint) collapses into one edge-computed boolean** · 2026-08-29 · Accepted
- **Context:** B5 (surface unused + duplicate/redundant indexes) was pre-committed to Phase 2 (`project.md` pre-commitments, ADR-0022) *because* "unused" is only honest over the snapshot **time window** Phase 2 introduces — a point read of `pg_stat_user_indexes.idx_scan` can't tell a never-used index from one queried the second before you looked. The engine already had the pure/IO seam; the open questions were *where* the rule lives, *how* "unused" stays honest, and *how* the safety invariant (never recommend dropping a unique / PK / FK / constraint-backing index) is enforced without leaking catalog complexity across the wire.
- **Decision:** (1) **Pure analyzer, server-driven.** `IndexHygieneAnalyzer` (engine pure half, no I/O) takes the existing indexes + a per-index `IndexScanWindow` and emits `IndexHygieneFinding`s — `DUPLICATE` (exact structural twin: same method/columns/predicate), `REDUNDANT` (a strict leading prefix of a wider index, same method/predicate), `UNUSED` (zero scan growth over the window). At most one finding per index, priority `DUPLICATE > REDUNDANT > UNUSED` (a structural twin is a stronger, always-safe removal than "unused over a window I may not have watched long enough"). It is fixture-testable with no DB, mirroring the plan-detection seam. (2) **Honest "unused."** The agent forwards *cumulative* `idx_scan` in the `CatalogSnapshot`; `IngestService` appends it to the `index_stats` time-series each ingest; `HygieneRepository.scanWindows` deltas the first vs. last snapshot per index. Only indexes with ≥2 snapshots get a window, and a **backwards** delta (a stats reset) is dropped as inconclusive — so a reset is never mistaken for "unused" (mirrors the ADR-0024 reset honesty). (3) **The guard is one edge-computed boolean.** `CatalogReader` marks `constraint_backed` TRUE when the index backs a PK/UNIQUE/EXCLUSION constraint (`pg_constraint.conindid`) **or** its leading key columns cover a FOREIGN KEY's referencing columns (matched by name in Java against `pg_constraint.contype='f'`). Folding FK-coverage into the *same* boolean at the edge means the whole guard list travels as one field — no FK data on the wire, no schema for it — and `IndexInfo.guarded()` (`unique || primary || constraintBacked`) is the single check the analyzer honours by skipping such an index outright. Findings are **derived state**: each pass *replaces* this db's `index_hygiene` rows (V3), so a since-fixed index stops appearing. Advisory only — PgLens never drops anything.
- **Alternatives:** put the rule entirely in the server (loses the pure unit-testability the seam gives every other detector; the redundancy logic is pure and belongs with `detect`) · judge "unused" from a single `idx_scan` read (dishonest — indistinguishable from "used a moment ago"; the whole reason B5 waited for Phase 2) · a fixed "unused for N days" threshold (a magic constant; instead the finding *states* the observed window and snapshot count, and the user judges) · model FK-supporting indexes as their own wire field + schema column (more contract + migration surface for a flag that only ever gates a drop — collapsing it into `constraint_backed` at the edge is strictly simpler and errs safe: at worst it over-guards, never under-guards) · treat every guarded twin as droppable and pick by heuristic (unsafe — a plain index must always yield to the constraint index, never the reverse).
- **Consequences:** B5 is delivered honestly: `DUPLICATE`/`REDUNDANT`/`UNUSED` over the real snapshot window, and by construction **no** unique/PK/FK/constraint index is ever flagged — proven at three levels: the pure analyzer IT (guard never fires even for a zero-scan unique index; priority; prefix/method/predicate discrimination), the `CatalogReader` IT against the real image (a PK is `constraint_backed`+guarded with a real `definition`+`idx_scan`; an index added on the FK column `orders.customer_id` is marked `constraint_backed` though non-unique), and the server hygiene-flow IT (a duplicate pair → one `DUPLICATE`, a flat index → `UNUSED`, a flat *PK* → never flagged, a backwards counter → not "unused", a resolved duplicate cleared on re-run). The V3 migration adds `index_hygiene`. The hygiene fields promised in ADR-0028 are now populated end to end. **Deliberately deferred:** cross-table duplicate detection (indexes are compared within a table only), and surfacing a hygiene finding through the REST/GraphQL API (Phase 4 — the finding is persisted and queryable now). FK-coverage matching is a leading-prefix name match (schema-qualified / multi-schema edge cases ride the single-schema MVP assumption already noted for `CatalogSnapshot`).

## ADR-0030
**A dedicated least-privilege `pglens_ro` login role on the monitored DB — defense in depth over the session guard; closes ADR-0020's deferred item** · 2026-08-29 · Accepted
- **Context:** Charter principle #2 requires the monitored DB be safe *by construction*. Phase 1 enforced read-only via the **session** guard (`SET SESSION CHARACTERISTICS AS TRANSACTION READ ONLY`, ADR-0020) but explicitly deferred a DB-level read-only **role** to Phase 2 "when the agent connects." Phase 2's agent now logs in continuously and on a schedule, so this is the moment to close it. The question isn't whether to have the role but *what least-privilege role can do everything PgLens genuinely needs* — sample **all** of `pg_stat_statements` (not just its own rows), read the catalog, and run **edge HypoPG** validation — while being physically unable to write.
- **Decision:** A dedicated `pglens_ro` login role, provisioned by the monitored image's initdb (`deploy/compose/monitored/initdb/20_pglens_ro.sql`): `NOSUPERUSER NOCREATEDB NOCREATEROLE NOBYPASSRLS`, granted only `pg_read_all_stats` (full visibility into `pg_stat_statements` text + `pg_stat_user_indexes` — without it another role's query text redacts to `<insufficient privilege>`), `USAGE` on `public`, and `SELECT` on all current + future tables. **No write grant on anything.** hypopg's functions are PUBLIC-executable by default (a hypothetical index is session-local and writes nothing to the catalog), so they need no grant — edge validation runs *as this very role* inside the read-only transaction (ADR-0020 already proved hypopg works read-only). CONNECT and schema USAGE ride PUBLIC's defaults, so the script names **no database** and stays portable across the compose db (`pglens_demo`) and the Testcontainers one. The agent's `application.yml` already defaults its monitored-DB URL to `pglens_ro`. This is **defense in depth**: the session guard (ADR-0020) and the role's privileges each reject a write *independently*.
- **Alternatives:** rely on the session guard alone (one layer — a later refactor that dropped the `SET … READ ONLY` would silently regain write ability; the role is the backstop) · omit `pg_read_all_stats` (then the agent can't see other roles' query text — defeating the point of monitoring the whole DB) · `GRANT EXECUTE ON ALL FUNCTIONS IN SCHEMA public` for hypopg (over-broad — would also grant `pg_stat_statements_reset`; hypopg's PUBLIC default already suffices, and least privilege beats convenience) · a full ownership/RLS scheme (YAGNI for a read-only observer) · provision the role via a Flyway migration (wrong DB — the role lives on the **monitored** DB, owned by its image/initdb, not PgLens's metadata store).
- **Consequences:** the monitored DB is now safe at **two independent layers**. Proven against the real image by `ReadOnlyRoleIntegrationTest`: as `pglens_ro` over the agent's guarded connection, `StatsReader` sees the superuser's statement *text* (so `pg_read_all_stats` is working), `CatalogReader` reads, and a full HypoPG validate returns `PLANNER_VALIDATED` with `hypopg()=0` afterward; and on a plain **unguarded** `pglens_ro` connection an `INSERT` is rejected with "permission denied for table orders" — the role's own guarantee, not the session's (Spring wraps it, so the test asserts on the stack trace). The image doesn't bake initdb in (compose mounts it as a volume), so the harness gained `MonitoredDbContainer.initReadOnlyRole` to apply `20_pglens_ro.sql` over JDBC the same way it applies the schema. Real deployments would harden further (revoke PUBLIC CONNECT, scope USAGE per schema); the demo relies on PUBLIC defaults for portability, documented in the script header. Closes the DB-level read-only-role item ADR-0020 deferred to Phase 2.

## ADR-0031
**Trend queries read the persisted delta series honestly: "new" = first-ever row in the window, and every derived ratio is NULL-not-fabricated when its denominator is zero** · 2026-08-29 · Accepted
- **Context:** Phase 2 Step 7 adds the trend/leaderboard layer over the `query_stats` delta time-series (ADR-0024): a query's `mean_exec_time` over time, week-over-week **top movers**, and **new-slow-query** detection. Three sub-decisions carry honesty weight (principle #1) rather than being mechanical SQL: what "new" means, how a movement is quantified when there's nothing to compare against, and how the mover list is ordered. Full REST/GraphQL is Phase 4 — Step 7 builds only the `TrendRepository` + `TrendService` seam the integration test drives (YAGNI).
- **Decision:** (1) **"New" = genuinely absent from history, not merely quiet last window.** `newQueries` returns a query only when its *earliest* `query_stats` row falls inside the recent window — a `NOT EXISTS` anti-join against any row before `recentFrom`, plus a `HAVING sum(total_delta) >= minTotalMs` "slow" floor. A query that ran a month ago, went quiet, and returned is **not** new (it has prior history); classifying it as new by comparing only two adjacent windows would be a lie the data can already refute. (2) **Derived ratios are NULL when their denominator is zero.** The pure `TrendMath.percentChange(recent, prior)` returns `null` when `prior <= 0` (a newly-active query has no baseline — a ratio there is a fabricated ∞, not a measurement), and `TrendMath.mean(total, calls)` returns `null` when `calls == 0` (0/0 is undefined, never reported as 0). Split into a no-Spring `TrendMath` so those boundaries are unit-tested with no container. (3) **Top movers rank by absolute `deltaMs` descending** (worst regression first), carrying the nullable percent change as context — so a new load with no prior still ranks on its real absolute delta instead of being dropped for lack of a ratio. Windows are a **service-owned policy** (recent vs. the equal-length window before it — week-over-week by default), passed explicitly so tests are deterministic; the repository only sums measured deltas.
- **Alternatives:** define "new" as "zero in the prior window" (cheap, but mislabels a returning query as new — dishonest) · report percent change as 0 or a large sentinel when prior is 0 (fabricates a number where none exists) · report window mean as 0 for zero calls (same fabrication) · rank movers by percent change (explodes to ∞ for new load and buries a huge absolute regression that happened to start from a non-trivial base) · push all derivation into SQL (harder to unit-test the honesty boundaries; the null-vs-fabricate rule is exactly what deserves a fast no-DB test) · pre-add a `captured_at` index to speed the cross-query window scan (that scan is the **Step 11 dogfood target** — indexing it now would erase the before/after the benchmark exists to measure).
- **Consequences:** the three DoD trend questions are answered over the real series, proven by a Testcontainers IT (a regressed query ranked above an improved one; a first-in-window slow query surfaced with a `null` percent change and a real mean; a new-but-trivial query filtered by the floor; an established query never called "new") and a no-DB `TrendMathTest` pinning the null boundaries. `windowTotals`/`newQueries` deliberately scan `query_stats` by `captured_at` range across all queryids — the exact cross-query access path the PK doesn't serve and the dogfood benchmark will index — so the code comments and the `V1__init.sql` note both mark it "do not index here." No new migration, no new ADR-0030 collision (0030 stays reserved for the Step 8 read-only role per the plan). Surfacing these through an API is Phase 4; the service seam is shaped for it.

## ADR-0033
**The withheld `query_stats` trend index = `BRIN(captured_at)` (V4), chosen on measured evidence over a `btree(db_id, captured_at)`** · 2026-08-29 · Accepted
- **Context:** V1 deliberately withheld a `query_stats` time-series index (its DOGFOOD NOTE) so Step 11 could *measure* the cross-query trend scan and pick the index on evidence. The trend/top-mover queries (`TrendRepository.windowTotals`/`newQueries`) scan `query_stats` by `captured_at` **range across all queryids** — a path the V1 PK `(db_id, queryid, captured_at)` doesn't serve (captured_at is the 3rd key column). The dogfood benchmark (`scripts/dogfood_benchmark.sh`, `make bench`) backfilled **2.1 M rows** (120 queries × 26 weeks @ 15-min, **363 MB**, inserted in `captured_at` order as ingest really appends) into the real V1–V3 schema on the pinned `pgvector:0.8.6-pg16` image and ran `EXPLAIN (ANALYZE, BUFFERS)` on the verbatim trend SQL (parallelism + JIT off; median of 5 warm runs).
- **Decision:** add **`BRIN(captured_at)`** as **`V4__query_stats_trend_brin.sql`** (default `pages_per_range`). **Measured** (all numbers in `docs/benchmarks.md`): on `windowTotals` the V1 PK drove a `Nested Loop` of 120 per-query range scans that heap-fetched every row in the 14-day window — **~162,961 buffers**, ~101 ms warm; BRIN cut it to a `Bitmap Heap Scan` over the ~2,228 physically-contiguous window blocks — **~2,238 buffers (~73×)**, ~85 ms, for a **24 kB** index. A `btree(db_id, captured_at)` gave the same read reduction (~2,309 buffers) and a marginal warm wall-time edge (~77 ms) but cost **15 MB** (~625× larger) and real per-insert page-split maintenance. `captured_at` is append-only and physically time-ordered — the textbook BRIN fit — so BRIN wins the trade decisively.
- **Alternatives:** `btree(db_id, captured_at)` — measured, and the right call *only* for a many-tenant metadata store where per-db isolation beats time-window pruning; deferred to **backlog B11** (YAGNI: Phase 2 is single-tenant, and 15 MB + write amplification buys nothing now) · pre-adding it in V1 (rejected by charter: the whole point was to *measure*, then add — a benchmark you can dogfood, not an assumed index) · a partial index — nothing to filter on here (the scan wants the whole time window) · leaving it unindexed — the ~73× buffer blow-up on the leaderboard path is exactly what a Postgres index advisor should not ship on its own store. **Honesty caveats recorded in the doc:** warm wall-time *understates* the win (the 363 MB table fits in OS cache) — **buffers** is the cache-independent, scale-relevant metric; the row *values* are synthetic (only table size + physical order are load-bearing); and `newQueries` barely moves (~1.25×) because it is bound by the first-seen `NOT EXISTS` anti-join, which the PK *already* serves correctly — so the trend index helps the cross-query aggregation, not the anti-join, and we don't over-index it.
- **Consequences:** the trend leaderboard scan now rides a 24 kB index instead of touching ~163k buffers; ingest pays near-zero index-maintenance cost (BRIN summarizes appended block ranges, kept current by autovacuum). BRIN's win depends on the physical/time correlation of `captured_at` (heavy out-of-order backfill or clock-skewed multi-agent interleaving would blunt it — `brin_summarize`/autovacuum mitigate). The dogfood note in `V1__init.sql` and the "leave it unindexed" language in `TrendRepository`/`server.md` are now **fulfilled** (updated to point at V4 + this benchmark). `make bench` + `scripts/dogfood_benchmark.sh` are the reproducible harness; `docs/benchmarks.md` is the writeup. Server ITs are unaffected (they assert on results, not plans); the new V4 migration is covered by the existing Flyway-on-boot IT.

## ADR-0034
**Validation-queue lifecycle: a revalidate cooldown + terminal-job retention (F1, shipped); lease-reclaim + dead-letter (F4, deferred to B12)** · 2026-08-30 · Accepted
- **Context:** An independent end-to-end re-verification of Phase 2 (post-Step-12) found work-queue lifecycle gaps the original build missed, none of which are charter/correctness/safety violations but two of which are real defects. **(F1)** `AnalysisRepository.enqueue`'s inflight-unique arbiter dedupes only `PENDING`/`LEASED`, so the instant a job went `DONE` the every-30 s analysis pass re-enqueued the same candidate again → `validation_jobs` grows unboundedly *and* the agent re-runs edge HypoPG on every candidate every tick (the "idempotent re-run" test missed it — it re-ran while the job was still `PENDING`). **(F4)** a job stuck in `LEASED` (agent crash / a validation that throws before reporting) stays `LEASED` forever, and the inflight-unique then blocks re-enqueuing that candidate. (Two lower findings from the same pass: **F2** idle queries wrote zero-`calls_delta` `query_stats` rows; **F3** the "§10 no-lost-window" DoD item was labeled onto the *reset* test rather than a genuine dropped-batch test.)
- **Decision (F1, shipped):** gate `enqueue` to skip a candidate whose `recommendations` row was updated within a **revalidate cooldown** (`pglens.analysis.revalidate-after-ms`, default **1 h**): `INSERT … SELECT … WHERE NOT EXISTS (a rec with updated_at >= now − cooldown)`. A recently-validated candidate is not re-validated until its verdict ages out — at which point it *is* re-validated, so a stale verdict still refreshes (e.g. gets retracted once the user adds the index, catching catalog drift). Plus a **retention prune** in the singleton analysis pass (`pglens.analysis.job-retention-ms`, default **7 d**) deleting terminal (`DONE`/`FAILED`) jobs — the verdict lives on in `recommendations`, so it loses no advice and bounds the queue. IT-tested: cooldown-blocks-then-refreshes-after-aging; aged-terminal-jobs-pruned. **(F2)** `DeltaCalculator.delta` now returns empty for a zero-`calls` interval (no idle-query row; the anchor still advances via the caller's unconditional cumulative upsert). **(F3)** added `IngestFlowIntegrationTest.aDroppedSampleLosesNoActivityInTheNextDelta` — the real ack-anchored no-lost-window proof, distinct from the reset test.
- **Decision (F4, deferred → backlog B12):** lease-reclaim + dead-letter is **not** patched inline — it is a schema change (an `attempts` column + a `(leased_at) WHERE state='LEASED'` reclaim index = a new migration) plus two tuning constants (lease-timeout, max-attempts) and a fencing-token design, i.e. a real reliability feature that must be chosen deliberately: a too-short timeout double-runs a legitimately-slow live validation, and a missing fence lets a stale worker clobber a re-leased job (reintroducing the very double-processing it exists to prevent). The researched, chosen shape (recorded in B12): a lease-timeout janitor folded into the *singleton* analysis pass (LEASED older than the timeout → `PENDING`, or → `FAILED` past max-attempts), an `attempts` counter for dead-lettering poison candidates, and an attempts/epoch fence on `recordResult`. PgLens's validation is hypothetical/read-only/idempotent, so double-processing is **low-harm** — F4 is robustness, not a correctness hole, its blast radius is one stuck candidate (the loop keeps flowing), and it is not a Phase-2 DoD item — so it earns the same deliberate treatment as B10/B11, not a rushed patch.
- **Alternatives:** (F1) re-validate every pass (rejected — the defect) · never re-validate after the first verdict (rejected — can't retract a rec after the user adds the index; misses catalog drift) · gate on a plan/catalog *version* rather than a time cooldown (more precise but needs version tracking — the cooldown is the KISS choice and still catches drift within the hour). (F4) a dedicated janitor scheduler (rejected — the advisory-locked analysis singleton is the natural already-periodic home) · reclaim with no fence (rejected — reintroduces double-processing) · no attempts cap (rejected — a poison candidate would reclaim-loop forever) · fix it inline now (rejected — schema + tuning + fencing is a feature, and it interacts with the F1 cooldown/retention just shipped).
- **Consequences:** the queue no longer grows unboundedly and edge HypoPG no longer re-runs every candidate every tick; a validated candidate re-validates at most hourly, and terminal jobs are pruned after a week. A crashed-mid-lease job stays stuck until B12 (bounded: it only blocks re-validating that one candidate). **[Superseded in part by ADR-0035]** — the reclaim + dead-letter half of F4 was later pulled into the v0.0.3 hardening patch (a stuck LEASED job no longer permanently blocks its candidate); only the epoch fencing token remains in B12. New config: `pglens.analysis.revalidate-after-ms`, `pglens.analysis.job-retention-ms`. Server tests **11 unit / 27 IT** green; `.claude/rules/server.md` updated. This audit + fix pass is the kind of end-to-end re-verification the charter's "ship each phase" bar expects before a tag.

## ADR-0035
**Phase 2 hardening (v0.0.3): fence-less lease-reclaim + dead-letter closes F4/G1; ingest-idempotency (G7) and no-lost-window (G4) claim corrections; a terminal-job report guard (G6)** · 2026-08-30 · Accepted
- **Context:** A second independent end-to-end re-verification of Phase 2 (after the ADR-0034 audit) confirmed no charter/safety/correctness violations and all 9 DoD items met (153 tests, re-run fresh). It then filtered the remaining gaps by a sharper question — *which have no downstream owner AND should be closed as an honest Phase-2 close-out?* Most are owned elsewhere and stay deferred (B10/Phase-4 registration API; Phase-6 mTLS; PG17-only eviction edge; Phase-5 HPA split). Four are **orphans or a mis-deferred correctness gap**: **G1/F4** a stuck `LEASED` job permanently blocks its candidate (silently drops a recommendation); **G6** `recordResult` accepted a report for any job state; **G7** an overstated "idempotent on `captured_at`" claim; **G4** a "no lost window" claim that reads as no-data-loss.
- **Decision:** (1) **Pull the *reclaim* half of F4 in, keep *fencing* deferred.** ADR-0034 deferred all of F4 to B12 treating a fencing token as intrinsic; on re-examination the two halves are separable with very different value/cost. The reclaim is the valuable half and is **safe fence-less in this topology**: `AnalysisRepository.reclaimStuckLeases` (run in the singleton advisory-locked pass) returns a `LEASED` job whose `leased_at` is older than `pglens.analysis.lease-timeout-ms` (default 5 min) to `PENDING` bumping `attempts`, and dead-letters it to `FAILED` past `max-validation-attempts` (default 5); migration **V5** adds the `attempts` column + `validation_jobs_leased_idx`; `enqueue` gains a **poison-cooldown** (skip a candidate with a recent `FAILED` job, reusing the F1 revalidate cooldown) so a deterministically-throwing candidate can't churn. (2) **G6** — `recordResult`'s job lookup requires `state IN ('PENDING','LEASED')`, so a stale/late report for a `DONE`/dead-lettered job is ignored, not resurrected. (3) **G7** — corrected the claim: the cross-send no-double-count guarantee is the atomic anchor-advance, not `captured_at` dedup (server-assigned, kept as the skew-immune axis). (4) **G4** — sharpened every "no lost window" claim to "no lost query **totals**; missed intervals collapse into one delta point (resolution, not data, loss); no disk buffer."
- **Why fence-less is safe here (the crux):** the fence prevents a *stale worker clobbering a re-leased job* — a hazard that needs ≥2 concurrent validators on one db. PgLens is **one single-threaded agent per db** (token = db identity; the `@Scheduled` loop can't re-lease a job it's still validating), and `recordResult` upserts idempotently on `(db_id, queryid, ddl)` plus the new terminal-state guard — so there is no double-write hazard today. A generously-set lease timeout (5 min ≫ a seconds-long validation batch) means a merely-slow live validation is never reclaimed. The fence becomes load-bearing only under true concurrent workers (Phase-5 scale), so it stays in **B12** (YAGNI).
- **Alternatives:** ship the full fence now (rejected — speculative complexity for a race that can't occur in a single-agent-per-db topology; YAGNI) · keep all of F4 deferred per ADR-0034 (rejected — backlog ≠ scheduled; the plan of record ships after Phase 4, so B12 may never land, leaving a real "recommendation silently never appears if the first validation attempt crashes" bug in a shipped product) · a dedicated reclaim scheduler (rejected — the advisory-locked analysis singleton is the natural already-periodic, already-single-instance home) · no attempts cap (rejected — a poison candidate would reclaim-loop forever) · no poison-cooldown (rejected — a dead-lettered candidate would re-enqueue every pass) · for G7, re-key idempotency on the agent's sample epoch to make replay genuinely safe (rejected — reintroduces clock skew into the trend axis for a replay path the stateless agent never exercises) · for G4/G7, just leave the wording (rejected — a Postgres *honesty* tool overstating its own durability/idempotency is exactly the charter-#1 self-audit that should catch itself). This **amends ADR-0034's F4** and **narrows B12** to just the fencing token.
- **Consequences:** a stuck `LEASED` job self-heals within one lease-timeout and a genuinely-poison candidate is dead-lettered instead of looping — the only gap that could silently degrade core output is closed, fence-lessly and cheaply (one additive migration, ~3 server classes). New config: `pglens.analysis.lease-timeout-ms`, `pglens.analysis.max-validation-attempts`. Proven by new ITs (a timed-out lease → `PENDING` +attempts; past the cap → dead-lettered; a fresh lease untouched; a recently-dead-lettered candidate not re-enqueued until the cooldown; a report for a terminal job ignored) + the Flyway IT extended to 5 migrations. Server tests **11 unit / 33 IT** green (+6); full `./gradlew build` green. G5 (a literal server-restart IT) was considered and **skipped** — the §10 self-check's intent is already proven by the dropped-batch IT, and `GrpcServerLifecycle`'s OS-assigned port makes a faithful restart test brittle for mostly library-reconnect coverage. Ships as **v0.0.3** (a Phase-2 hardening patch, like the ADR-0034 audit — not a new phase).
